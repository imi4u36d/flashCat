同一批数据、同一套卡片规格，差别只在信息优先级。表中的「实现成本」按现有概览页的布局原语估算，不含聚合逻辑本身。

建议

先做 A，把 B 的排行留在同一个页面里

A 与你给的参考同构，迁移风险最小；而它的底部本来就有按模型排行，B 的核心价值（谁在干活、谁更快）已经覆盖了八成。 等真实用上几个月、模型分布稳定，再把排行提上来做 B，删掉六格里的重复项——那时数据也撑得起更大的版面。

C 的日历信息密度最低，但它回答了另外三个方向都没回答的问题：什么时候在用。如果这个问题的价值高于总量，就选 C。

  • 方向A（推荐）／ B ／ C，或「A 的六格 + B 的排行」。
  • 缓存命中率要：给消息补 cachedPromptTokens 落盘（值本来就在内存里）。不要：首屏换成平均解码 47.2 tok/s，指标零改动。
  • 时间窗保留 7 天 / 30 天 / 全部三档，还是只留 30 天 / 全部？「全部」实际是本机保留的最近 200 段会话。
i

每个数从哪来

除缓存命中率外，全部指标都能从现有落盘消息直接算出来，不需要联网、不需要新增存储。

指标口径现状
会话 / 消息本机会话数与 user + assistant 消息数；chat-history.json 保留最近 200 段已有，重启保留
Token 总量每条 assistant 消息的 promptTokens + completionTokens 求和已有；图片 / 视频轮可能为 0
活跃天数 / 日历消息 createdAt 按本地时区归日；没有时间戳的旧导入消息不计已有
最常用模型按 assistant 消息的 model 聚合；会话归属给它消息最多的模型已有；需要这条归属规则
平均解码消息 tokensPerSecond 的 token 加权平均（网关打点口径）已有
缓存命中率cachedPromptTokens ÷ promptTokens缺落盘：值在内存里，StoredMessage 没写；只能统计上线后的新消息
时间窗筛选按消息 createdAt 过滤后重算，纯函数，不改存储新增聚合函数即可

注意：会话保留上限是 200 段，更早的会话被裁掉后，「全部」的总量会跟着下降。页脚写「本机保留最近 200 段会话」就是为了说明这件事。
